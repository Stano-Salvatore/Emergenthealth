## 1. The sync question, answered

**The server half needs nothing.** Oura, Strava, YNAB, TrueLayer, Last.fm and
RescueTime are pulled every 30 minutes by `.github/workflows/sync-cron.yml`,
with the daily Vercel crons underneath as a floor and a dead-man's switch on
top. Oura has offered webhook subscriptions since v2, which would turn that
poll into a push — but a 30-minute poll against a ring that publishes a night
once a day is not the thing that is wrong, and a webhook adds a public
endpoint and a subscription that has to be renewed. Not worth it.

**The phone half is where "easier sync" lives.** Health Connect is
`driver: "device"` in `sync-status.ts` for an honest reason — it only runs
when the app is running:

- `HealthConnectAutoSync.tsx` fires on `visibilitychange`, throttled to once
  an hour, from inside the WebView.
- `readLast30Days()` re-reads all eight record types over 30 days on every
  one of those runs, and POSTs 30 days of upserts.
- A week without opening the app is a week with no steps, no phone-side
  sleep and no weight — the same shape of hole the weather cron was built to
  close, and for the same reason: the data is missing on exactly the days the
  app was not opened, which is not missing at random.

**What is new since that design.** Two things, both platform-level:

1. **Background reads.** `READ_HEALTH_DATA_IN_BACKGROUND` lets an app read
   Health Connect after the system has put it in the background. Google's
   own guidance pairs it with WorkManager for the periodic sync.
2. **Change tokens.** `getChanges` returns what was added, changed or deleted
   since the last read, instead of re-reading a month. Tokens expire after 30
   days, so the fallback is a full time-range read and a fresh token — which
   is exactly the 30-day read this app already does, kept as the cold path.

**Neither is reachable from JavaScript here.** `@kiwi-health/capacitor-health-connect`
is on 0.0.42 (June 2026) and exposes `readRecords` and permissions, nothing
more; the maintained alternatives (`capacitor-health` 8.2.0,
`@capgo/capacitor-health` 8.11.3) add iOS and aggregates but read fewer of the
record types this app needs and expose no background path either. Swapping
plugins buys nothing for this problem.

So the easier sync is real and it is **native**: a small Health Connect worker
under `android-widget/`, reading with the androidx client and POSTing with the
widget key — no WebView, no session, exactly the shape `EmergyLocationService`
already proves works on a Samsung that kills services without saying so. The
15-minute watchdog is already there to keep it alive. It costs an APK, and it
is the single biggest reliability win left on the phone.

**And the Samsung watch needs no special plumbing.** Samsung Health has
mirrored watch data — steps, exercise, heart rate, sleep — into Health Connect
since version 6.22.5. There is no reason to reach for the Samsung Health Data
SDK, a Health Sync app or a Google Drive hop: Health Connect is already the
short path, it is just only walked while the app is on screen.

## 2. What this pass found that the audit did not

1. **Health Connect filed two hours of every night under the wrong day.**
   `dateStr()` in `health-connect-service.ts` was
   `d.toISOString().slice(0, 10)` — the UTC day, computed on the user's own
   phone. In CEST every record between local midnight and 02:00 landed on
   yesterday: the steps walked home after midnight, the calories burned with
   them, a weight taken before dawn, each then read against the wrong night's
   sleep by the correlation engine. **Fixed in this change**, with a test that
   sets a timezone rather than assuming one (CI runs in UTC, where the bug is
   invisible and a test that does not set one passes on the broken code).
   The standing UTC guard did not catch it because it matches
   `.<timestampField>.toISOString()`, and this was a bare local variable in a
   helper.
2. **A failing Health Connect sync is still indistinguishable from a quiet
   one, away from the Settings card.** `permissionsByType()` landed on the
   20th and the Settings card now names the types this phone refuses, which
   is the half a user can act on. The other half is untouched: `safeRead()`
   swallows a per-type read error into an empty array, `HealthConnectAutoSync`
   swallows the POST failure entirely, and the status screen infers the
   source's health from `health_connect_last_sync` — a preference written
   only on success. A phone that has been syncing into a 500 for a week reads
   as a phone nobody picked up. The per-endpoint `EndpointOutcome` machinery
   in `sync-status.ts` already exists for Oura, and `permissionsByType` is
   now the missing list to fill it with.
3. **The chat prefix carried a finances section on a build with no finances.**
   `claude.ts` read 100 `Transaction` rows and printed "## Finances (this
   month) … No spending yet." on every cache write, for a feature `features.ts`
   holds back. **Fixed in this change**: the query and the section are gated on
   the flag and on there being rows, matching how screen time is written.
   (Audit A13.) The screen-time query beside it is now in the same position:
   with B1 answered — this build says it cannot read screen time —
   `screenTimeLog` can never have a row on the APK, so the read is dead
   weight even though the section it feeds is already gated on rows.
4. **`AutoSync` re-syncs four providers on every app open** while GitHub
   Actions is already pulling the same six every 30 minutes. Throttled to 30
   minutes locally, so it is small — but it is also where the smoke run's
   400s come from, and the freshness it buys is at most half an hour.

## 4. What to do, in order of payoff against effort

1. **Native Health Connect sync (APK).** A WorkManager worker or a watchdog
   tick that reads Health Connect and posts with the widget key. Removes the
   one data source that silently stops when the phone is not touched. Batch it
   with A12 and C10, which are waiting on an APK anyway.
2. **Say when the phone's sync failed.** Have the sync POST carry per-type
   outcomes into the same `EndpointOutcome` shape Oura uses, so a refused
   permission stops reading as a quiet week. Web plus a small client change;
   no APK.
3. **Incremental reads.** Until there is a plugin path to change tokens,
   narrow the warm read to the last seven days when the previous sync
   succeeded and keep the 30-day read for the cold start. Thirty upserts an
   hour become seven, and revisions to last week's sleep still land.
4. **Set `EMERGY_CHAT_EFFORT=medium`** and read a week of `[emergy] turn`
   lines. Still one environment variable, still the biggest cost lever.
5. **A2, B3, B4, C7** — a cleanup session, all web.

## 5. What is in good shape

Worth writing down, because a review that only lists faults misreads the
codebase. The server syncs are honest about their own failures and say so on
the status screen; the correlation engine spends a shared FDR budget and
guards its own sentences; the scripted answers cannot disagree with Emergy
about a number because they read the same helpers; the chat bill is now
itemised per feature; and the standing guards catch, by grep, the four classes
of bug that kept coming back. Nothing in this review is structural.
